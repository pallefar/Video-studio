<objective>
Rebuild the four Wan 2.2 A14B templates as what the model actually is.

Every one of them currently loads a single checkpoint file into a single loader and runs a
single sampler. Wan 2.2's 14B variants are a two-expert mixture: a high-noise expert for the
early denoising steps and a low-noise expert for the late ones, published as separate files
per quant level. A single-loader graph is not a graph with a small wiring bug; it is a graph
of the wrong shape. Research Pitfall 1 is explicit that patching the clip and vae edges
alone produces a template that passes a structural audit and still fails at runtime, because
the checkpoint filename it names does not exist as a single combined file.

So this plan does the rebuild, and folds the other wiring defects into it rather than fixing
them twice: the three-loader split so no clip or vae edge is taken from a diffusion loader,
and the three video-combine fields the pack declares required.

It also fixes something worse than either, found by the reachability sweep plan 03-01's audit
now performs. Three of these four templates contain a node that their own output node cannot
reach. `wan2.2-i2v` declares a source image required, uploads it, patches its filename into
an image-loading node — and nothing in the graph reads that node's output, so the sampler
generates from the prompt alone. `wan2.2-vace-fun` does the same with its source video.
`wan2.2-fun-camera` does the same with its camera-embedding node, which means every camera
preset ever generated through this template applied no camera motion at all; the preset's
prompt text did all the work. None of the three errors. All three return a plausible clip.
Rebuilding the architecture without connecting these would ship four correctly-shaped graphs
that still ignore their inputs.

And it fixes the shape desynchronisation that would otherwise make the M10.6 benchmark
measure a broken graph: `wan2.2-fun-camera` patches frame count and resolution into its
latent node while its camera-embedding node keeps the hardcoded 832 by 480 by 33 it shipped
with. A five-second clip request produces an 81-frame latent and a 33-frame camera embedding.

Purpose: this is the structural half of runbook step 8 and the precondition for M9.1's first
real clip. Every line of it is CPU-provable before a card is rented.
Output: four A14B templates of the correct shape, audited clean, with the exact step boundary
left as a documented workstation tunable.
</objective>
