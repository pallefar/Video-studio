<objective>
Wire the phase's dead code into a real, running path: CPU loop preprocessing finishes →
a GPU cache-build stage runs → MuseTalk's own cache files land in ObjectStore → the
BaseLoop points at them → a later render can load them back.

`build_loop_cache` has exactly one occurrence in this repository — its own definition
(`worker_gpu/preprocess/loop_cache.py:13`). Nothing enqueues it, no route calls it, no
stage chains to it. The most important thing this plan delivers is not the cache format;
it is that the path exists at all and is exercised by a test on every commit.

The model call is isolated behind ONE seam: a `prepare(source, out_dir)` callable that
writes MuseTalk's own filenames into a scratch directory. Everything on either side of
that seam — dispatch, GPU locking, idempotency, upload ordering, the ObjectStore bridge,
column invalidation, download-and-restore — is built and proven here on a CUDA-less Mac.
Phase 1's real engine plugs into the seam in plan 02-03.

Purpose: runbook step 4's implementation half (docs/workstation.md §5), M2.3.
Output: a live dispatch chain, a GPU cache stage, and a persisted-cache bridge whose only
unimplemented part is the model call itself.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: Lock the cache artefact layout and the two-column mapping</name>
  <decision>Where the three MuseTalk cache files live in ObjectStore, and how they map onto `BaseLoop`'s two existing URI columns (`latents_uri`, `bbox_uri`).</decision>
  <context>
This is effectively one-way. The moment a loop is cached on the workstation, its columns
hold URIs in whatever shape is chosen here, and every later loop follows. Changing it
afterwards means a migration plus a re-build of every cached loop on the GPU host — the
expensive half. Deciding it before the tracer writes the first key costs nothing.

The constraint driving this: `packages/schema/models.py:202-203` gives `BaseLoop` exactly
two URI columns (`latents_uri`, `bbox_uri`), but MuseTalk's preparation produces up to
three files worth persisting (`latents.pt`, `coords.pkl`, `mask_coords.pkl`). Two columns,
three artefacts.

Also settled here by implication: per-frame PNGs (`full_imgs/`, `mask/`) are NOT persisted
in any option. They are the largest thing MuseTalk's cache produces (hundreds of MB) and
the cheapest to regenerate — `full_imgs/` is just decoded frames of the loop's own
`source_uri`, re-extractable with the ffmpeg call `worker_cpu/ffmpeg/loops.py::_extract_frame`
already makes. Persisting them would erode the transfer-time margin the ≥40% acceptance
criterion depends on.
  </context>
  <options>
    <option id="option-a">
      <name>Two columns, bbox_uri as a prefix (RESEARCH.md recommendation A4)</name>
      <pros>No Alembic migration; this phase stays pure worker code. Matches the existing `loops/{loop_id}/pingpong.mp4` key convention. Three separate small keys, individually resumable, matching the project's one-key-per-artefact convention everywhere else (`tts_segment_key`, `lipsync_chunk_key`, `derived_prefix`). `latents_uri` points at `loops/{id}/cache/latents.pt`; `bbox_uri` points at the `loops/{id}/cache/bbox` prefix holding `coords.pkl` and `mask_coords.pkl`</pros>
      <cons>`bbox_uri` is a prefix while `latents_uri` is a file — the two columns no longer mean the same kind of thing, which is a small readability cost in the schema</cons>
    </option>
    <option id="option-b">
      <name>Three columns — add `mask_uri` via an Alembic migration</name>
      <pros>One column per artefact; every URI column means the same thing; no prefix/file ambiguity</pros>
      <cons>Requires a migration, a schema change, and a `python packages/schema/export_ts.py` regeneration, for one small optional file whose necessity (P1-C) is not even resolved yet. Turns a worker-only phase into a schema phase</cons>

      <name>One `loops/{id}/cache/` prefix plus a `manifest.json` listing members</name>

Implement `worker_gpu/preprocess/loop_cache.py`. Keep the existing module docstring's
promises and extend it to describe the chosen layout from Task 1.

Define the key helpers as module-level functions so both this module and its tests have
one source of truth: `cache_prefix(loop_id)`, `latents_key(loop_id)`, `bbox_prefix(loop_id)`,
`coords_key(loop_id)`, `mask_coords_key(loop_id)`. Define the MuseTalk filename constants
(`LATENTS_FILENAME`, `COORDS_FILENAME`, `MASK_COORDS_FILENAME`) separately from the key
functions, because the filenames are MuseTalk's contract and the keys are ours. Document on
`bbox_prefix` that the column it backs names a prefix rather than a single object, so a
reader of the schema is not misled.

Define `cache_is_present(store, loop)` returning whether the loop has a live cache: the
`latents_uri` column set AND the object it names actually present in the store. Both halves
matter — a column pointing at a deleted blob must read as a miss, not a hit, or the loop
looks cached forever and silently skips its own rebuild. `ingest_stage`'s `store.exists`
check before treating derivatives as present is the precedent.

Implement `build_loop_cache(store, loop_id, prepare)` returning whether a build happened.
The `prepare` parameter is a callable taking the downloaded source path and an output
directory, writing MuseTalk's own filenames into that directory and returning nothing. This
parameter is the entire reason the function exists in this shape: it is the single seam
where CUDA enters, and it forces the caller to hand in the already-resident engine's
sub-models rather than letting this module construct a second set of multi-gigabyte weights
(CLAUDE.md: models load once at worker boot and stay resident; RESEARCH.md Pitfall 2). The
body, in order: open a session and load the `BaseLoop`, raising if absent; return early if
`cache_is_present`; create a `tempfile` scratch directory; download the loop's source
through `ObjectStore.get_file` after `parse_uri`; call `prepare` with the source path and a
fresh subdirectory of the scratch; verify the two required filenames were produced and
raise a clear error naming the preparer if not; upload the required files and the optional
mask-coords file if it exists; only after every upload returned, set `latents_uri` and
`bbox_uri` and commit once. Everything local lives inside the `tempfile` scratch and is gone
when the function returns.

Implement `load_loop_cache(store, loop_id, dest_dir)` — the reverse bridge, returning the
destination directory on a hit and nothing on a miss. It downloads the cache objects into
`dest_dir` using MuseTalk's OWN flat filenames at the directory root, not our S3 layout.
That asymmetry is deliberate and is the point of the function: the S3 key layout is this
phase's choice and may change, while the flat directory layout is MuseTalk's `Avatar`
contract (its own paths are the avatar directory root plus each filename) and must mirror
it exactly, so a future caller can point MuseTalk's own preparation-skipping code path
straight at the directory. Skip the optional mask-coords file when its key is absent.

Portability, enforced by `tests/test_portability.py` against every file under `worker_gpu/`
and `worker_cpu/` and applying to docstrings as well as code, since only `#` comments are
stripped: no builtin file-opening call — use `Path.write_bytes`, `Path.read_bytes`, and
ObjectStore; no http-scheme URL; no direct boto3; no absolute path literal beginning with a
system directory; no hardcoded service address; no `BaseSettings` definition. In particular,
if this module ever serializes anything itself, it must go through `Path.write_bytes` with
the serialized payload rather than a file handle. Nothing here imports torch — serialization
of the latents belongs entirely inside `prepare`, on the GPU host, where torch exists.

Add `loop_cache_stage(loop_id)` to `worker_gpu/stages.py`, decorated with the stage timer
under a `loop_cache` stage name. Unlike the render stages, this one's timing ref is
genuinely the loop id, so the plain decorator is correct here. Order matters: resolve the
engine and check `cache_is_present` BEFORE acquiring the GPU lock, so a no-op never takes
the card away from a waiting render. Obtain the preparer from the resident lip-sync engine
returned by `get_engines()` using `getattr` for a `prepare_loop_cache` attribute; if the
engine does not expose one — which is the case today, and is the case under `DEV_ENGINES=1`
on any Mac — log a loud structured warning naming the engine class and return without
touching the columns. That keeps `./scripts/dev_up.sh` and the CI suite green while making
the Phase-1 dependency visible in the logs rather than as a crash. Then run
`build_loop_cache` inside `gpu_lock(get_redis(), HOLDER_RENDER)`, re-raising `GpuLockHeld`
unchanged as the render stages do, and letting any other exception propagate after logging —
there is no job row to fail here, the loop simply stays uncached and a re-enqueue retries.

Chain the dispatch in `worker_cpu/stages.py`. Add a module constant naming the GPU stage's
import path, and a small module-private helper that enqueues it on `QUEUE_GPU` with
`stage_key(loop_id, "loop_cache")` as the job key, wrapped in try/except with a structured
warning exactly like `ingest_stage`'s caption chain — direct invocation in tests and scripts
has no Redis and must not break. Call it at the successful tail of `loop_preprocess_stage`,
after the existing commit, guarded on `loop.error is None`. This lives inside the stage and
never in the route handlers: both `POST /loops` and `POST /loops/{id}/preprocess` already
funnel through this one stage function, so putting the chain here gives the manual rerun
