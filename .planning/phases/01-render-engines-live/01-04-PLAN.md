<objective>
Turn plan 01-03's tracer into measured evidence on the RTX 3090: both models resident,
a real 10 s clip, a real 5 s lip-sync, and an honest peak-VRAM number under 20 GB.

`scripts/bench.py --smoke` exists but today only calls `.load()` on both engines — it
never renders anything and it measures VRAM with `torch.cuda.max_memory_allocated()`,
which counts only the torch caching allocator. Roadmap success criterion 2 requires
strictly more: Chatterbox producing a 10 s clip, MuseTalk lip-syncing 5 s, both resident
simultaneously, peak VRAM logged under 20 GB. And the honest VRAM figure matters beyond
this phase — Phase 3 has to fit a 16-22 GB Wan model on the same card with no margin
(CONCERNS.md), so an understated number here becomes an OOM later.

This plan closes the four measurement boxes the whole phase has been building toward.
Everything that can be proven on a Mac already has been; what remains genuinely needs the
hardware, and it is gated as a human checkpoint rather than dressed up as an automated
criterion.

Purpose: runbook step 2's acceptance half (docs/workstation.md §5). Ticks M0.2, M0.3,
M0.4 and M3.1.
Output: a smoke harness that actually renders, and the phase's first measured numbers.
</objective>

Rewrite `smoke()` in scripts/bench.py so it proves what roadmap criterion 2 actually

Resolve the render inputs first, before loading any model, so a misconfigured host fails
in two seconds rather than after a multi-GB load: add `--voice` and `--base-loop` options
that take entity ids, defaulting to the most recently created VoiceProfile and BaseLoop in
the database. Name the loop selector `--base-loop`, not `--loop`: `--loop` is already taken
by the M2 cache-benchmark mode and the two live in a mutually exclusive group, so reusing

speech, using `make_segments` so the segment is shaped exactly as the real pipeline builds
it. Give the job a title that plainly marks it as a bench artefact so it is recognisable
if it ever appears in the panel. Register a cleanup that deletes the job and segment rows
when the run ends, pass or fail — a bench row left sitting in `queued` looks like a stuck
render. Leave the S3 artefacts in place: they are the evidence, and the operator will want
to listen to and watch them.

Reset peak memory stats, then load both engines and keep both references alive for the
whole run — the point of the measurement is simultaneous residency, so nothing may fall
out of scope early.

Render through the real public methods, never through private helpers or a re-implemented
inference path: call `synthesize_segment` for the segment, then `sync_chunk` for the window
from 0 to 5000 ms. Probe both returned artefacts and print their measured durations. Assert
the TTS clip is at least 10 s and the chunk is 5 s within a small tolerance; a clip that
came back at the wrong length means the format or timeline contract is broken even though
nothing raised. Print the chunk's stream layout too, so the video-only requirement is
visible in the transcript.

Fix the VRAM measurement. `max_memory_allocated` counts only torch's caching allocator: the
CUDA context and MuseTalk's mmlab CUDA ops sit outside it, so today's figure understates
the real occupancy of a card that Phase 3 has to share. Print three numbers — torch
allocated peak, torch reserved peak, and the device-level figure from `nvidia-smi`
`--query-gpu=memory.used` sampled while both models are resident — and judge
`VRAM_BUDGET_GB` against the device-level figure, falling back to the reserved peak when
`nvidia-smi` is unavailable. Label which figure the budget was applied to, so the number
that later lands in the docs is unambiguous.

Delete the now-dead `NotImplementedError` catch and its "blocked on engine implementation"
message.

In tests/test_render_engines.py, add CPU-only tests for the parts that do not need CUDA:
that `--smoke` and `--loop` remain mutually exclusive and one is required, that `--voice`
and `--base-loop` parse alongside `--smoke` without colliding with the `--loop` mode, and
that `smoke()` exits 1 with a message rather than a traceback when `_require_gpu` refuses. Do not attempt to fake CUDA to test the render path —
that would manufacture a green signal for the one thing this plan exists to measure.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bench harness -> production database | The smoke creates and deletes real RenderJob and Segment rows on the workstation's live database |
| bench harness -> the GPU | The smoke loads both models and holds the card outside the render lane's Redis GPU lock |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-13 | Tampering | bench-created RenderJob rows in the live database | medium | mitigate | The bench job is titled as a bench artefact and its rows are deleted in a cleanup that runs on both success and failure, so no bench row can be mistaken for a stuck render in the panel |
| T-01-14 | Denial of Service | bench holding the GPU without taking the Redis lock | medium | accept | The runbook runs the smoke as a deliberate single-operator step before any worker is started (docs/workstation.md §5 step 2); adding lock acquisition would make the harness depend on Redis for no benefit at this point in the sequence. Task 2's instructions state the worker is started only afterwards |
| T-01-15 | Information Disclosure | smoke artefacts left in the object store | low | accept | Left deliberately as the operator's evidence; they land in the same private bucket as every other artefact, and ObjectStore exposes no way to make an object public (compliance C5 by construction) |
| T-01-16 | Repudiation | measured figures recorded in docs | low | mitigate | Every figure is annotated with its date, source measurement and device string, so a later reader can tell what was measured versus estimated |
</threat_model>
