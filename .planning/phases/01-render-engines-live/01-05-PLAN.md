<objective>
Expand the tracer from one window to many, and drive the whole thing from the panel.

Plan 01-03 rendered a single window starting at the loop's first frame. That is correct
for one chunk and wrong for two: the dev engine restarts the base loop from frame 0 for
every chunk, so with real MuseTalk a multi-chunk video would jump back to the loop's
opening frame at every boundary — a visible seam roughly every 60-90 seconds, which is
exactly what roadmap success criterion 4 forbids. Fixing it is small and precisely
locatable: each chunk must resume at the loop frame where the previous one ended.

Then the phase's real payoff — a script goes into the panel and a finished, watchable,
watermarked video comes out with nobody touching a terminal. Every layer beneath that is
already built and tested; this is the first time all of them run together with real
models.

Purpose: runbook step 3 (docs/workstation.md §5). Ticks M3.4 and closes the phase.
Output: seam-free multi-chunk lip-sync and the first real end-to-end avatar render.
</objective>

  <behavior>
    - Test 1: `loop_frame_offset(0, fps, frame_count)` is 0, and `loop_frame_offset(start_ms, fps, frame_count)` for a start beyond one full loop wraps modulo `frame_count` — the loop cycles, it does not run out
    - Test 2: offsets chain — for contiguous windows from `chunk_windows`, the offset of window N+1 equals `(offset of window N + frames rendered in window N) % frame_count`. This is the seam-free property, expressed as an assertion
    - Test 3: non-integer frame counts are handled without drift — for a window length that is not a whole number of frames at the loop's fps, accumulated offsets across ten consecutive windows stay within one frame of the exact value rather than drifting linearly
    - Test 4: chunk durations sum exactly to the total span — given a segment list, the sum of `end - start` over `chunk_windows(spans)` equals `sum(spans)`, and each chunk MuseTalk is asked to produce is exactly its window's length
    - Test 5: a chunk whose key already exists in the store is skipped on a re-render while its siblings still render — the segment-level retry behaviour M3 requires, asserted over a three-window job with the middle chunk pre-populated
    - Test 6: `sync_chunk` requests loop frames from the prepared-loop memo rather than re-preparing per chunk — assert the preparation runs once across three windows for the same loop id
  </behavior>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| panel -> API -> render job | Operator-submitted script text enters the pipeline; validated at the API edge by the existing Create schemas, unchanged by this plan |
| GPU worker restart -> partially rendered job | A job resumes against artefacts written by a previous process |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-17 | Tampering | resumed job trusting pre-existing chunk objects | medium | mitigate | Chunk keys encode the exact window bounds, and windows are a deterministic pure function of segment spans, so a stale chunk can only be reused for the identical window; Task 1 Test 5 asserts the skip-and-render-the-rest behaviour and Task 2 step 10 verifies it on hardware |
| T-01-18 | Tampering | C1 watermark on the first real render | high | mitigate | The watermark is applied structurally in the already-shipped assembler with no enable-window and no off-switch, and is covered by frame sampling at 10/50/90 percent in tests/test_assemble.py; Task 2 additionally requires a human to confirm it is visible throughout both previews |
| T-01-19 | Repudiation | measured render performance | low | mitigate | Stage durations are recorded to the metrics table by the existing `timed_stage` decorator, so the figures written into docs are traceable to rows rather than to recollection |
| T-01-20 | Denial of Service | a long script producing many resident prepared loops | low | accept | The in-memory preparation memo is keyed by loop id and a single job uses one loop; growth is bounded by the number of distinct loops a worker sees between restarts, which is small for a single-user tool. Bounded eviction belongs with Phase 2's persisted cache, not here |
| T-01-21 | Information Disclosure | first real render reaching the review gate | low | accept | Uploads land private by construction and no code path sets public visibility (C5); this plan stops at `review` and adds no publish path |
</threat_model>
